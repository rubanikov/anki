# speedrun/eval/pset — the P-set (H2)

Held-out items, and the run that produced them. **This directory is the only
place item text lives.** It is desktop-side, outside the Collection, and outside
anything that syncs to a phone: an item in a note would let the student read the
whole held-out set out of the card browser, and Performance measured on items the
student has read is not a measurement.

| file | what it is |
|---|---|
| `generate_pset.py` | the driver. It does not generate — `speedrun/agent/` does |
| `h2_pset.jsonl` | the items. Append-only; each row's id and hash are in the H2 ledger |
| `run_log.jsonl` | one row per generation attempt: concept, question type, outcome, and the reason if it dropped |
| `QUALITY.md` | the honest read — how many of these items would actually be shown to a student, and the ten that would not |
| `check_no_leak.py` | reads the Collection and reports whether any item text is in it. The acceptance criterion says *checked, not assumed* |
| `out/` | the service's own attempt ledger and trace for this run. Local evidence, regenerated by re-running; **not committed** |

`speedrun/eval/holdout/h2_pset.jsonl` is a byte-identical copy. That path is
named by the H2 protocol, which was frozen before this ticket and whose script
(`freeze.py`) reads it; the path is not ours to move, so the file is written in
both places and the driver copies the bytes rather than re-serialising them.

## Running it

```bash
speedrun/agent/.venv/Scripts/python speedrun/eval/pset/generate_pset.py --plan
speedrun/agent/.venv/Scripts/python speedrun/eval/pset/generate_pset.py --run
python speedrun/eval/pset/check_no_leak.py            # no item text in the Collection
python speedrun/eval/holdout/freeze.py --verify       # ledger matches the items
```

`check_no_leak.py` opens each collection read-only and immutable, and takes
`--collection <path>` for whichever collection the demo runs on; with no argument
it checks the local Anki profile and the demo deck's `.apkg`. On this machine
that is 2 885 notes, in which **no item stem and no item id appears**. Twelve
bare answer strings do — `apoptosis`, `glycolysis`, `S phase` — which is what a
Bio/Biochem deck is *supposed* to contain and is reported separately so the check
cannot be mistaken for a stricter one than it is.

`--plan` prints every attempt without calling a model, which is the cheap way to
see that the requests differ before paying for them. `--run` resumes: ids keep
counting up from what is already in `h2_pset.jsonl`, and an item already in the
set blocks a duplicate of itself.

## What this driver is responsible for

The gate, retrieval, the model call and the rejection ledger are all
`speedrun/agent/`'s and are used unmodified. Two things are this script's.

### 1. Requests that are genuinely different

The previous sweep sent the **same prompt three times per Topic** — `seed`
selects among the *stub's* canned claims and is never passed to a model — so 27
attempts yielded 20 distinct citations. Three copies of one item is one item.

Each attempt here differs in three ways at once:

- **a target concept**, taken from the AAMC Outline's own itemised topic list for
  that category (`corpus/outline.json`). Four per Topic, at evenly spaced
  positions through the list, so four attempts land in four different corners of
  a category rather than four times in its opening paragraph;
- **the retrieved passages**, because the concept is prepended to the Outline
  query BM25 runs — different attempts on one Topic read different pages;
- **the question type**, rotated through four fixed forms (identification,
  function, mechanism, discrimination).

The concepts are AAMC's words, chosen by a stated rule rather than by hand, so
`--plan` prints the same plan every time.

**What is deliberately not used to force variety:** the answers already
accepted. Telling the model "do not repeat these" would put item text into a
generation prompt, which is Leakage under the H2 protocol and exactly what the
leakage check (T-20) looks for. Distinctness is bought with the Outline and the
corpus, never with the set itself.

### 2. Asking for an item a student could be given

The Generation gate proves an answer is **grounded**. It cannot tell a term from
a whole sentence lifted out of the prose, and the previous sweep shipped two of
the latter — perfectly cited, useless as exam items. The driver appends to the
service's prompt the constraint the gate cannot check: a short, specific answer
(a term, a name, a number, at most about six words), distractors of the same kind
and length, and a stem that reads as a self-contained exam question rather than a
comprehension question about a passage.

## Deviations, stated rather than buried

1. **The prompt is the service's, plus an addendum.** `speedrun/agent/` keeps one
   prompt for both providers so that a Yield comparison stays a retrieval
   finding; this run adds item-quality constraints on top of it. **These items
   are therefore not comparable with the Yield table in the agent's README** —
   the yield in `QUALITY.md` is the yield of a different, stricter request. The
   SHA-256 of the exact prompt each item was produced under is on the item
   (`prompt_sha256`), and the addendum is in `generate_pset.py`.
2. **`max_output_tokens` is 8000, not the constructor's 4000.** One observed
   attempt spent 2112 tokens reasoning before writing a 60-token item; a
   truncated response is counted as `generator_empty`, which would report a
   budget artefact as a generator declining. Nothing else is reconfigured — same
   model, same schema, provider-default reasoning effort.
3. **The retrieval query is the Outline query with the concept in front of it.**
   `topics.py` fixes the query as the category's title plus its topic list; the
   concept added here comes from that same list. It is never the candidate
   answer, which is the property that matters: a query derived from the answer
   would hand the gate the string it is about to look for.

## Ledger discipline

Every item is written to disk and appended to the H2 ledger in `MANIFEST.md` by
`freeze.py --append-item --set H2` **as it is produced**, before the next attempt
starts. The protocol's rule is that an item's id and hash are in the ledger
before the item is shown; nothing here shows anything to anyone, and the ordering
is kept literally anyway.

H2 is left **open**, not closed: more items can still be added. `--close-set H2`
fixes the file-level hash and is for whoever adds the last one.
