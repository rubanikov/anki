# Performance bench — 50,000-card synthetic deck

> ## This deck is SYNTHETIC and never reaches a score
>
> Every card, tag and review in the collection benchmarked here was generated by
> `gen_deck.py` from a fixed seed. It exists to make the backend do a realistic
> amount of work so that **latency** can be measured. It is not a student, it is
> not a study history, and it is not evidence about anything else.
>
> **No Memory, Performance or Readiness value computed from this deck is
> recorded in this file, in `results.json`, or anywhere else, and none may ever
> be reported.** Calibration is measured against a real review-log corpus
> ([ADR-0001](../../docs/adr/0001-calibration-uses-a-public-review-log-corpus.md)),
> mastery against a real deck
> ([ADR-0005](../../docs/adr/0005-the-sensor-is-a-real-public-deck-not-one-we-author.md)).
> A score read off invented review history would be a number about our own
> random number generator.
>
> The collection carries the same warning in its own config
> (`speedrunSyntheticBench`) and in every deck description, so nobody who opens
> the profile can mistake it for a real one.

**Result in one line: the two backend calls are fast enough on their own, and
the dashboard that makes nine of them is not. On this debug build the dashboard
gather misses its PRD §10 targets by 6.7× (first load) and 12.5× (refresh).
A debug build is not a release build, so this is a flag, not a verdict — see
[Build profile](#build-profile).**

### Build profile

`_rsbridge.pyd` is the **debug** build. No release `rsbridge` exists in this
tree (`out/rust/release/` holds only `rsdroid.dll`, the Android JNI library),
and this ticket is explicitly read-only measurement, so nothing was rebuilt to
get a release number.

This matters more than any single figure below:

* **A debug-build number that misses a target is not evidence that the release
  build misses it.** Rust debug builds carry no inlining and full bounds
  checking; the ratio on this workload is unknown and is not assumed here.
* Where a target is missed, this file states **the factor by which a release
  build would have to be faster for the target to be met**, and marks the
  target `MISSED (debug)` — never `MISSED`, and never quietly `PASS`.
* Re-running `bench.py` against a release `rsbridge` is the outstanding work.
  The command is unchanged; only the `.pyd` differs.

## The deck

Built by `gen_deck.py`, **seed `20260802`**, into a throwaway `ANKI_BASE`.

```bash
python speedrun/eval/bench/gen_deck.py \
    --base "$SCRATCH/ankibase50k" --cards 50000 --seed 20260802
```

| | |
|---|---|
| Study cards | 50,000 (one card per note) |
| Speedrun attempt cards | 372, suspended, tagged `speedrun::holdout` — excluded from every measurement by design, and present so the exclusion query has rows to exclude |
| Total cards / notes | 50,372 |
| Review-log rows | 219,687 |
| Cards with FSRS memory state | 40,990 |
| Collection file | 41.3 MB |
| Anki database check | passes — `"Database rebuilt and optimized."`, no problems, run on a copy |

### Card mix, and why it is mixed

Topic resolution is most of the per-card cost, so a deck that resolves the same
way for every card would measure one branch and report it as the whole.

| segment | cards | tags | what the crosswalk does with it |
|---|---:|---|---|
| native | 10,000 | `mcat::<SEC>::<topic>`, all 31 content categories | resolved from the note's own tags; the crosswalk is never consulted |
| mapped | 25,000 | the 32 MileDown tags `miledown-bb-v1` maps | resolved by the crosswalk |
| refused | 5,000 | the 6 MileDown tags it deliberately refuses (`topic: null`) | refused, counted unmapped |
| unmapped | 10,000 | 21 Chem/Phys, OChem, Psych/Soc and unrelated labels it has never seen | **full 38-entry scan, then unmapped** — the worst case per card |

Review history is simulated per card: 18% of cards are never reviewed, the rest
get an expovariate number of reviews (mean ≈ 5.3, capped at 40) with growing
intervals and a 12% again-rate. FSRS memory state is **not** written into the
card data column by hand — it is computed by Anki itself from the generated
revlog (`update_deck_configs(fsrs=True)` → `Collection::update_memory_state`),
so the `fsrs::current_retrievability` call in `mastery.rs` is doing the same
arithmetic on the same shape of input it would in a real collection.

### The crosswalk was installed

`speedrun/crosswalk/miledown-bb-v1.json` (`id: miledown-bb-v1`, 38 entries) was
installed via `col.set_config("speedrunCrosswalk", …)` for the primary run.
Resolution is part of the query cost, and a run without it understates real
latency — so both configurations are reported and **the crosswalk run is the
one the targets are judged against**, since it is what ships.

Denominators the calls actually produced:

| | crosswalk installed | no crosswalk |
|---|---:|---:|
| cards considered | 34,219 | 10,000 |
| cards unmapped | 15,781 | 40,000 |
| cards excluded (attempt cards) | 372 | 372 |
| topics resolved | 31 | 31 |

The 15,781 unmapped with a crosswalk installed is 5,000 refused + 10,000 never
seen + **781 cards the crosswalk maps but this deck's deck-paths do not
qualify for**: the `MileDown::Biology::Immune_System` entry is restricted to
`decks: ["MileDown's MCAT Decks::Biology"]`, and the synthetic deck tree is
named `SYNTHETIC — Speedrun bench (never scored)::…` precisely so it cannot be
mistaken for the real one. Those cards fall through to unmapped. That is
correct behaviour and it is stated here rather than left as an unexplained 781.

## Method

* **The dashboard gather is the add-on's own code path.** `bench.py` imports
  `speedrun/addon/backend.py` directly and issues the same nine calls in the
  same order as `dashboard._gather`. It does not import `dashboard.py` itself,
  which pulls in `aqt` and a Qt event loop; the Qt half is what makes the
  UI-blocking targets unmeasurable here.
* **Warm-up discarded:** 3 iterations before every warm timing series, 2 before
  the cold series, 3 before the grading series. Discarded iterations are not
  included in any figure.
* **Iterations recorded:** 20 per backend call, 20 per dashboard gather, 10 per
  cold open, 50 for grading.
* **p95 is nearest-rank**, not interpolated — an interpolated p95 over 20
  samples invents a value that was never observed. Where nearest-rank p95 lands
  on the maximum (n ≤ 20 for the cold series), `results.json` says so with
  `"p95_is_max": true`.
* **Every individual sample is in `results.json`** (`samples_ms`), in the order
  taken, so the spread can be checked rather than trusted.
* **Machine load** was sampled before and after each configuration and recorded.
  It is not hypothetical: an earlier run of this same bench, on a busier
  machine, is preserved as `results-contended.json` and is up to **2.8× slower**
  on the no-crosswalk configuration (`TopicMastery` ALL p50 1257 ms vs 451 ms).
  That run predates the load snapshot, so what else was running was not
  captured and the cause cannot be pinned down — which is itself the reason the
  snapshot was added. `results.json` is the quieter run; the slower one is kept
  rather than deleted, because reporting only the faster of two runs and not
  mentioning the other is how a benchmark lies. (It was produced by an earlier
  revision of `bench.py`, before per-sample recording, and its
  `database_check.problems` field is mangled by a bug fixed since.)
* **No score value is read.** `bench.py` times the calls and discards the
  responses apart from the denominators above; `grep -c "estimate\|readiness"`
  over both result files returns 0.

### Dashboard first load and refresh — the miss

This is the real finding, so it gets stated plainly. **On this debug build the
dashboard misses both of its targets, in both configurations, at p50 as well as
p95.** For the shipped configuration to meet them, a release build would have to
be **≥ 6.7× faster** for first load and **≥ 12.5× faster** for refresh on this
workload. Neither factor is established, and neither is claimed here.

But part of the cost is not a build-profile question at all:

* `dashboard._gather` makes **9 backend calls** — `SectionScores` and
  `TopicMastery` for each of CP, BB, PS and CARS, plus one collection-wide
  `TopicMastery`. Eight of them (all but `SectionScores` for CARS) read every
  card in the collection.
* `SectionScores` **calls `TopicMastery` internally**
  (`rslib/src/speedrun/scores.rs`), then `_gather` calls `section_mastery` for
  the same section separately. Each section's 50,372 cards are therefore scanned
  **twice per section**.
* The arithmetic holds exactly: 6268 ms ÷ 8 full scans = 784 ms, which is the
  measured single-call p50 to within a millisecond. The gather is not doing
  anything the individual calls do not; there are simply eight of them.

So roughly **half the gather is redundant work**, and that half is redundant at
any build profile. Fixing it is not this ticket's scope — it lives in
`speedrun/addon/dashboard.py` and `rslib/src/speedrun/` — but it should be
recorded as the first thing to try, ahead of a release re-run:

1. Have `_gather` reuse the `TopicMastery` that `SectionScores` already
   computed, instead of asking for it again (≈ 2× on the whole gather).
2. Resolve every section in one pass instead of one pass per section — the
   per-card work is identical; only the `section` filter differs (up to ≈ 4×
   more on top).

Both are read-side changes only, and neither touches a threshold or a score.

### Memory

Peak working set of the benchmark process, with the 50,372-card collection open
and every gather run, was **145.6 MB**. Both configurations report the same
figure because peak working set is process-wide and monotonic — the second
configuration cannot report less than the first already reached, so this is one
number for the whole run, not two that happened to agree.

**PRD §10 says "under a stated ceiling" and no ceiling is stated anywhere in the
PRD**, so this target cannot pass or fail — it can only be reported. It is
listed as unresolved rather than silently marked green.

Two caveats that stop this number being read as the desktop app's footprint:
it is a headless Python process — no Qt, no WebView, no rendered dashboard,
which on real desktop Anki dominate — and it says nothing about the midrange
phone the PRD also names.

### Next card after grading

`col.sched.answer_card()` followed by `col.sched.get_queued_cards()`, on a
throwaway copy of the collection so the seeded deck is not disturbed: **p50
1.16 ms, p95 1.51 ms, worst 1.79 ms** over 50 graded cards (3 discarded).

The PRD target is 100 ms and it is an *end-to-end* target. Question rendering,
the WebView round trip and the repaint are not in this number. The backend half
uses 1.5% of the budget, which means the target is not at risk from the backend
— it does not mean the target passes.

## What could not be measured, and why

Listed here rather than dropped. A performance report that silently omits the
targets it could not reach is the thing this project exists to oppose.

| target | why not |
|---|---|
| Button press acknowledged (p95 < 50 ms) | The acknowledgement is a Qt/WebView repaint. No Python API observes the moment a button visibly responds, and no backend number may stand in for it. Needs a GUI harness driving real input events. |
| Next card after grading, end to end | Only the backend half is reachable from Python. Rendering, the WebView round trip and the repaint need the GUI. |
| Dashboard never freezes; nothing blocks the UI > 100 ms | A property of the Qt event loop. `dashboard.py` runs the gather on a `QueryOp` background thread, which is a structural argument for it, not a measurement of it. |
| Normal session sync < 5 s | Requires an AnkiWeb account and a sync server. Not run. |
| Cold start < 5 s desktop / < 4 s phone | Process launch, Qt initialisation and the main window are outside this script. Collection open (5.3 ms p50) is one component of it and is not the target. |
| Memory on a midrange phone | Android. Not run here. |
| Zero corrupted collections across the crash test | The crash test needs its own kill-and-restart harness. `--integrity` here only shows the generated collection is well formed, which is a different claim. |
| Any target on Android ("both platforms", "midrange phone") | The `.aar` was not built or measured by this ticket. Every number above is desktop. |

## Reproducing

```bash
export PYTHONPATH=out/pylib          # the built bridge; nothing is rebuilt
export SCRATCH=/some/throwaway/dir   # never a real ANKI_BASE

python speedrun/eval/bench/gen_deck.py \
    --base "$SCRATCH/ankibase50k" --cards 50000 --seed 20260802

python speedrun/eval/bench/bench.py \
    --base "$SCRATCH/ankibase50k" \
    --integrity \
    --cold-reps 10 --cold-warmup 2 \
    --gather-reps 20 --gather-warmup 3 \
    --out speedrun/eval/bench/results.json
```

`bench.py --build-profile release` records the profile in the output; it does
not change what is measured. Pass it when the bridge is a release build.

**What the seed does and does not fix.** `random.Random(20260802)` fixes the
card mix, which tag each card gets, which cards have history, how many reviews
each gets and every interval — the whole shape of the work the backend does.
It does not fix note/card ids, guids or absolute review timestamps, which are
derived from wall-clock time, so two builds from the same seed are equivalent
but not byte-identical. Card counts, review counts and the resolution
denominators reproduce exactly — checked by building the deck a second time
into a different base: 50,372 cards, 219,687 reviews, 40,990 with memory state,
identical segment counts, and a file 25 KB different in size.

The generated collection is ~41 MB and is not committed — it is reconstructible
from the seed. `.gitignore` needs:

```gitignore
# --- Speedrun bench (T-22) — see speedrun/eval/bench/BENCH.md ---
# The 50k synthetic deck is 41 MB and rebuildable from the recorded seed, so it
# is regenerated rather than stored. Only the numbers commit. gen_deck.py
# requires --base and has no default, so nothing lands here unless someone
# points it at the repo; these entries are the guard for when they do.
speedrun/eval/bench/*.anki2
speedrun/eval/bench/*.anki2-*
speedrun/eval/bench/*.colpkg
speedrun/eval/bench/media*
speedrun/eval/bench/bench/
```

`results.json` and `results-contended.json` **do** commit — they are the
measurement.

## Re-run: release build, double scan removed

The two entries above were recorded as `MISSED (debug)` because a debug number
cannot decide a release target. Both causes have since been addressed, so the
verdict is now real.

**Two things changed.** The Rust bridge was rebuilt in release — the harness no
longer takes the profile on trust, it hashes the loaded extension against the
built artifacts and reports `detected: true`. And the dashboard stopped asking
the backend for each section's mastery after `SectionScores` had already
computed it, which was four extra full-collection scans per load.

**A third thing was wrong and is worth recording.** This script used to hold its
own transcription of the dashboard's read sequence. When the dashboard changed,
the transcription did not — so the first release re-run timed a code path that no
longer existed, and timed it *slower* than reality. The reads now live in
`speedrun/addon/backend.py::dashboard_reads`, called by both, so they cannot
drift apart again. The 2.3 s figure that intermediate run produced is discarded.

| measurement | debug, old path | release, current path | change | target | verdict |
|---|---:|---:|---:|---:|:--|
| Dashboard first load p50 | 6664 ms | **1190 ms** | 5.6× faster | < 1000 ms | **MISS**, by 19% |
| Dashboard first load p95 | 8145 ms | 1299 ms | | | |
| Dashboard refresh p50 | 6268 ms | **1075 ms** | 5.8× faster | < 500 ms | **MISS**, by 2.2× |
| Dashboard refresh p95 | 6418 ms | 1144 ms | | | |
| Peak working set | 145.6 MB | **130.9 MB** | | < 400 MB | **PASS** |

**Both dashboard targets are still missed, and that is the finding.** First load
is close enough that it is a tuning problem; refresh is not — at 50,000 cards the
remaining cost is five full scans of the collection, one per section plus the
collection-wide read, and no amount of build optimisation removes them. Meeting
500 ms needs the scans themselves to go: either `SectionScores` returning its
topic rows so the collection-wide read becomes unnecessary, or the backend
caching mastery against the collection's modification time.

Neither was attempted before the deadline. The number is reported as it stands.
